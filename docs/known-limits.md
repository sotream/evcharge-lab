# Known limits and production gaps

**The station gateway: missed in the first two runs, met in the rewritten one.** [ADR 0000](adr/0000-requirements-and-capacity.md) asks for at least 10,000 connections and at least 2,000 msg/s with CALLRESULT p99 under 500 ms per instance. One gateway holds 10,000 connections at a peak RSS of 525 MB ([`gateway-10k-connections.json`](load-output/gateway-10k-connections.json)). The first two k6 runs with the real `sessions` service behind it delivered 910.28 msg/s (1,000 stations) and 1,139.03 msg/s (2,000 stations) with p99 of 1,446 ms and 3,228 ms and zero CALLERRORs (measured, [`k6-gateway-ws-1000st-1hz.json`](load-output/k6-gateway-ws-1000st-1hz.json) and [`k6-gateway-ws-2000st-1hz.json`](load-output/k6-gateway-ws-2000st-1hz.json)). The review of November 2026 found that method flawed: 2,000 stations at 1 msg/s offer exactly the target, and k6 divided by the whole run including the connection ramp, so the rate could not reach 2,000 whatever the gateway did (the ceiling was about 1,545/s). The p99 miss was real in those runs. The script was rewritten (common steady window, 2,500 msg/s offered, unanswered CALLs counted) and run three times on the M4 Pro: [`k6-gateway-ws-2000st-1.25hz.json`](load-output/k6-gateway-ws-2000st-1.25hz.json) and its [repeats](load-output/gateway-ws-2000st-1.25hz-repeats-20261109T122949Z/NOTE.md) give 2,490 to 2,498 msg/s and p99 223 to 253 ms, so both targets are **met** in that series (measured). Method, Docker VM (11.7 GiB instead of 8.3 GB) and build all changed at once, so the series does not say why the first runs were so much slower, and the 1,139 / 3,228 ms figures stay in the table as missed. The stations in the new series are idle apart from heartbeats and meter values (no charging sessions), and the stack was cut down to one gateway, no HAProxy, no billing and no simulator, as in the first runs.

- **Bottleneck ([ADR 0004](adr/0004-websocket-connection-routing.md), measured amendment):** one Node.js core per instance. A single gateway process was observed at about 108% CPU during the first two runs (observed, not saved as a file, and not re-measured in the 1.25 Hz series; the saved 10,000-connection run is a different load, with `samples[].cpuPct` peaking at 110 in [`gateway-10k-connections.json`](load-output/gateway-10k-connections.json)). Per message it does a JSON parse, zod validation, a Kafka produce with `acks=all` through a pure-JS client, and a second produce for the raw log.
- **Raw-log experiment (unreproducible, not used as evidence):** an earlier experiment reported 802 and 1,068 msg/s with the raw log on and off. No file was saved, and the figures are inconsistent with the kept 2,000-station run (1,139.03 msg/s with the raw log on). The effect of removing the second produce is not measured.
- **The fleet requirement is not demonstrated:** the 2,400 msg/s design peak spread over 5 surviving instances is 480 msg/s per instance [derived: 2,400 / 5]. The newest series ran one instance at about 2,490 msg/s with p99 253 ms, which covers the per-instance rate; what is still not shown is the fleet: five instances behind HAProxy with the simulator's charging sessions and billing running at the same time.
- **Scaling path:** one gateway process per core (Node cluster or more replicas behind HAProxy; the registry already supports any number of instances), sampling or batching the raw log, and a precompiled validator instead of a per-frame zod parse.

**Other limits of the measurements**

- **The load generator shares the machine with the stack.** k6 and the simulator ran on the same physical machine as the services under test and competed with them for CPU and memory, so measured rates and p99 latencies can be worse than with a separate generator. A run from a second machine (`load/run-remote.sh`, see the [runbook](runbook.md)) was not made. Only one machine is used for every number in this repository.
- Everything is single-instance on one machine, and all containers share one Docker VM with the load generator (see the setup records: `docs/load-output/*.env.json` for k6, `docs/drill-output/*/env.json` for drills, and the setup note above for which machine and VM each series used). Absolute numbers are not production numbers; they show where each design stands against its own target.
- The sessions sweep is not monotone: at 150 commands/s the StartTransaction p99 was 621.77 ms, above the script's 500 ms threshold, while 200 commands/s passed with 177.39 ms. Each point is one 60 s run, and the cause of the 150/s outlier was not isolated.
- The smart-charging open-loop p99 of 19.45 ms ([`smart-charging-allocbench.json`](load-output/smart-charging-allocbench.json), measured) is close to its 20 ms target.
- Gaps in the evidence: no saved run measures the driver-api write p99 (target 800 ms), the telemetry visible-in-driver-api p99 (target 10 s), the remote-start SLOs or the invoice-after-session-end p99. Those targets in `load/targets.json` have no measurement behind them yet.
- The full-fleet storage sizes are extrapolated from a 5,000-station, 7-day sample and are labelled derived. Compression and query numbers were measured with the background policy jobs paused and run manually (notes in `docs/load-output/telemetry-backfill-*.json`).
- Drill results in the metrics table and the drill charts are regenerated from `docs/drill-output/`; a failed check appears as FAIL.
- **Slow-Postgres:** the clean run (162708Z) passes (item 23), but it built no backlog (peak consumer lag 0). Earlier runs failed because of a coincident Kafka leader move (150304Z, with a pre-fault p99 rise that is not isolated) and an overloaded lab VM (160959Z), and are kept as evidence. A partition leader move still stalls the gateway's produces for about 1.3-1.9 s across the tuned runs (1.7 s at most with the shipped setting), a named limitation of `@platformatic/kafka` (ADR 0012).
- **Lab VM limit:** three Kafka JVM brokers on one 8 GB Docker VM (the VM of the earlier k6 runs) show 100-170% CPU per broker (observed, not saved as a file) even at low traffic once memory gets tight (GC). Rolling restarts recover them. Measurements taken in that state were discarded and rerun, so the saved runs should be read as taken on a healthy VM, not a tight one.
- **Drill checks changed after a failed run (disclosed in each `NOTE.md`):** in `kraft-quorum-loss` the baseline of the RemoteStop counter moved from before the Kafka stop to after the quorum loss was confirmed (the first run failed `remote_stop_sent_during_outage` because two commands were produced while the nodes were still shutting down). That check proves little by itself, because without Kafka commands cannot be produced anyway; it only shows that nothing leaked out during the outage. In `slow-postgres` the check `ingest_lag_p99_s_after_recovery` (118 s, FAIL) became `ingest_lag_p99_s_90s_after_recovery`, measured 90 s after recovery instead of over the minute in which the backlog drained. The clean run (162708Z) passes, but it built no backlog (peak consumer lag 0), as stated above. These changes were made after seeing the failures, so the passing runs are evidence that the fixed checks pass, not that the first ones would have.
- **Drills need a connected fleet:** every drill aborts through `require_fleet` unless all stations are connected, so a drill never reports on an empty fleet (item 20).
- **Jaeger keeps at most 20000 traces** in memory (`mem_limit` 400m), so old traces disappear under load.
- **24 h offline replay:** failed and inconclusive ([`station-offline-replay-20261108T151006Z`](drill-output/station-offline-replay-20261108T151006Z/NOTE.md)). The 10-minute run at time scale 1 passed. In the 24 h run at time scale 60 the harness restored the simulator before the replay queue drained, so the result says nothing about loss. The rerun passed ([`station-offline-replay-20261108T190213Z`](drill-output/station-offline-replay-20261108T190213Z/result.json): queues empty after 40 s, 0 dropped, 0 of 123,652 probe readings missing, 0 duplicate rows).
- NOT_ENOUGH_REPLICAS cannot be provoked on the compose Kafka cluster, so that path is covered by a unit test with a failing producer ([gateway README](../services/station-gateway/README.md)). The two-broker drill therefore uses produce errors and buffer growth as its evidence, not the literal error code.
- The reconnect-storm drill disconnected 199 stations (`events.log` of the run; the default fleet has 200) and a warm Redis, not with the 833 connects/s of ADR 0003, and the billing service has no load measurement.

**Production gaps (lab simplifications, from the [runbook](runbook.md) and the ADRs)**

- **Accepted limitations from the November 2026 review** (login limiter, credential revocation delay, read-your-writes, billing currency, outbox ordering window, and others) are listed with their revisit conditions in [ADR 0021](adr/0021-accepted-limitations.md).
- **Service authentication:** a shared internal token instead of mTLS ([ADR 0010](adr/0010-authentication.md)).
- **Station security:** OCPP security profile 1 (Basic auth) instead of TLS client certificates ([ADR 0003](adr/0003-ocpp-subset-station-auth-and-offline-replay.md)).
- **Durability:** one primary with an asynchronous replica. The failover drills ([ADR 0018](adr/0018-postgres-failover-and-backup-restore.md)) measured that an asynchronous replica loses acknowledged commits when the primary dies, so RPO 0 holds only with a synchronous standby, which production needs.
- **Kafka:** combined broker and controller nodes; production would use dedicated controllers ([ADR 0012](adr/0012-kafka-replication-and-producer-backpressure.md)).
- **Simulator control API:** unauthenticated, bound to 127.0.0.1 only.
- **PSP:** a mock. A real adapter must support idempotency keys and voiding by authorization key ([ADR 0007](adr/0007-billing-saga-and-exactly-once-effect.md)).
- **Out of scope:** OCPI roaming, OCPP 2.0.1, ISO 15118, a real payment provider, multi-region active-active and grid or energy-market integration ([ADR 0000](adr/0000-requirements-and-capacity.md)).
